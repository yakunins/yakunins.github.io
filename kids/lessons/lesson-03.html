Theory

What Is a Protocol?

A protocol is a set of rules that two devices agree to follow so they can exchange information. Without protocols, your laptop and a server on the other side of the planet would have no way to understand each other — like two people trying to have a conversation in different languages with no translator.

The Internet relies on many protocols stacked in layers. At the bottom, TCP/IP handles addressing and delivery. Above that, HTTP governs how web pages are requested and served. FTP handles file transfers, SMTP handles email sending, and so on. Each layer has its own job, and together they make the Internet work.

HTTP vs. HTTPS — Why the “S” Matters

HTTP (HyperText Transfer Protocol) is the original protocol browsers use to fetch web pages. The problem: everything sent over plain HTTP travels as readable text. Anyone sitting between you and the server — a hacker on the same Wi-Fi, a rogue ISP employee — can read your passwords, messages, and credit card numbers.

HTTPS adds a security layer called TLS (Transport Layer Security, the successor to the older SSL). TLS encrypts the data so that even if someone intercepts it, all they see is scrambled nonsense. The padlock icon in your browser’s address bar means the site has a valid TLS certificate and the connection is encrypted.

Today, most websites use HTTPS by default. If a site still uses plain HTTP, your browser will often warn you that the connection is “not secure.”

TCP/IP: Splitting Data into Packets

When you download a photo or load a video, the data doesn’t travel as one giant block. Instead, TCP (Transmission Control Protocol) breaks it into small chunks called packets — typically around 1,500 bytes each. Every packet gets a sequence number so the receiving device can reassemble them in the correct order, even if they arrive out of sequence.

TCP also guarantees delivery: if a packet gets lost or corrupted along the way, TCP detects the gap and requests it again. This makes TCP ideal for web pages, email, and file downloads where every byte matters.

Its counterpart, UDP (User Datagram Protocol), skips the error-checking. UDP is faster but less reliable — perfect for live video calls and online games, where a slightly glitchy frame is better than a long pause while waiting for a lost packet.

Below TCP and UDP sits IP (Internet Protocol), which handles addressing and routing each packet from source to destination. Together, TCP/IP forms the backbone protocol suite of the entire Internet.

Ports: Doors into a Server

A single server can run dozens of services at the same time — a web server, an email server, a file server, a database. How does an incoming packet know which service it’s meant for? That’s where ports come in.

A port is a number (from 0 to 65,535) attached to every network connection. Think of an IP address as a building’s street address, and a port number as the apartment number inside that building. When your browser connects to a website, it sends data to the server’s IP address on a specific port:

  • Port 80 — HTTP (unencrypted web traffic)
  • Port 443 — HTTPS (encrypted web traffic)
  • Port 21 — FTP (file transfers)
  • Port 25 — SMTP (sending email)
  • Port 53 — DNS (domain name lookups)

Ports 0–1023 are called well-known ports, reserved for standard services. Higher port numbers are used by applications for temporary or custom connections.

Practice Task

Build: “Packet Splitter”

Create an HTML/JS page that simulates how TCP splits a message into packets and reassembles them:

  1. The user types a message into a text field and clicks “Send.”
  2. JavaScript splits the message into chunks of 3–5 characters each (these are your “packets”).
  3. The packets are displayed in a random, shuffled order — each one as a numbered card.
  4. After a short delay, an animation reorders the cards into the correct sequence.
  5. The reassembled message appears at the bottom.

Requirements:

  • An <input> or <textarea> and a “Send” button
  • Each packet displayed as a styled card showing its sequence number and content
  • Packets appear shuffled first, then animate into correct order using CSS transitions or setTimeout
  • The final reassembled message displayed clearly at the end
  • A “Reset” button to try again with a new message
